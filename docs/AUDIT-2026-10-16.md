## 2. ما هو حقيقي (لا نبخسه)

- **المصادقة:** Argon2id + JWT 15د + تدوير refresh مع claim-first update (نقطة تسلسل صحيحة) + كشف سرقة العائلة (`THEFT_DETECTED` + `security_events`) — تصميم ممتاز.
- **CSRF/CORS:** حارس Origin يفشل مغلقًا (fail-closed)، واستثناء صحيح للـwebhooks، وكوكيز `lp_access`/`lp_refresh` بخصائص HttpOnly/SameSite=Strict.
- **حل المستأجر من Host:** عبر `tenant_domains` (مع مشاكل كاش §5.6).
- **PolicyEngine:** 5 أدوار + ~22 فعلًا + مصفوفة RBAC كاملة (مع فجوات أدوار مفصلة في §6.4).
- **خدمات LMS:** امتحانات/واجبات/progression/enrollments/progress + مفاتيح idempotency + حجب `correctAnswer` في عرض الطالب الأساسي.
- **المدفوعات:** Paymob + Fawry بتنفيذ HTTP حقيقي + توقيعات + سجل قيد مزدوج + تقييم مخاطر.
- **حماية الفيديو:** watermark (mulberry32 + HMAC) + توكنات تشغيل + جلسات/Heartbeat/مخاطر — منطق رياضي حقيقي.
- **الويب:** 20 صفحة موصولة بـAPI حقيقي، التايمرات مشتقة من `expiresAt` السيرفر، والتسليم بمفاتيح idempotent.
- **اختبارات تعمل:** أُعيد تشغيلها مساء 16 أكتوبر — **179/179 api** (18 suite) + **51/51 web**، و`pnpm build` **4/4** — الشجرة خضراء حاليًا.

### 3.2 Feature Flags — ✅ أُصلح مساء 16 أكتوبر (commit `e9227bc`)

**الإصلاح:** `checkFeatureFlags` صار يقبل `flag === true || flag?.enabled === true`، مع اختبارَي انحدار (شكل boolean، وشكل `{enabled:false}` يرفض بـ`FEATURE_DISABLED`) — 179/179 api. الوصف التالي يوثّق العطل كما كان قبل الإصلاح.

- `policy-engine.ts:463-505` — السطر **488**: `const isEnabled = flags[featureFlag] === true;`
- `feature-flags.service.ts:304` — `getTenantFlags` ترجع `Record<string, FeatureFlagEvaluation>` أي **كائنات** `{ enabled, value }` وليست booleans.
- `authorization.service.ts:43-44` تمرر ناتجها إلى الـPolicyEngine، والنوع في `policy-engine.ts:57` هو `Record<string, any>` — لذا TypeScript لا يمسك الخطأ.
- **الأفعال المتأثرة:** `lesson:watch`, `video:watch`, `exam:attempt`, `assignment:submit`, `liveSession:join`, `certificate:create`, `community:create`, `analytics:read`, `ai:generate` → كلها ستُرجع `FEATURE_DISABLED` (403).
- الاختبارات الوحدية تمرر booleans مباشرة → تمرّ، والواقع يفشل.

**الأثر:** الحلقة الكاملة الموثقة في `docs/DEMO.md` لا يمكن أن تعمل حيًا قبل إصلاح هذا (محاولة الامتحان أول المتأثرين).

### 5.4 الفيديو

- "TUS" في Bunny توكن **مخصص** لا يقبله Bunny الحقيقي، وتوكن التشغيل كذلك — الجاهزية شكلية.
- `verifyWatermarkFromToken` يعيد بناء الحمولة بحقول فارغة → **دائمًا `valid:false`**.

## 6. حلقة LMS — الانحرافات البنيوية

### 6.1 Progression عالمي للـTenant وليس لكل طالب — ✅ أُصلح 17 أكتوبر (`e0ab627`)

**ما كان (سجل):** حالة الفتح على صف الدرس (`Lesson.lockStatus`)؛ قلب `UNLOCKED` يفتح الدرس المستهدف لكل طلاب الميزان؛ بلا `$transaction` فعلي وبلا قيود DB؛ `getNextLesson` بلا `tenantId`؛ والمتحكم يكرر الاستدعاء → `unlocked` دائمًا صفر.

**ما أُصلح:**

- جدول جديد `student_lesson_unlocks` (الجدول الـ43) بقيد `UNIQUE (tenantId, userId, lessonId)` + 4 سياسات RLS + FORCE + منح `app_user` (هجرة `20261017000001`).
- ENTER_ASSIGNMENT/ENTER_EXAM يكتبان **منحًا لكل طالب** داخل `$transaction` واحدة (`applyTenantContext` صريح) بـ`createMany`+`skipDuplicates` → idempotent على مستوى القاعدة تحت التكرار والتزامن (تحقق حي: إدراج مكرر مباشر → 23505؛ مسار `ON CONFLICT DO NOTHING` → 0).
- استدعاء progression مرة واحدة (من الخدمة) قبل تخزين استجابة الـidempotency، والاستجابة تحمل `unlocked` الحقيقي؛ المتحكم لم يعد يستدعيها ثانية.
- `getStudentProgression` وعرض الدرس للطالب يطبقان منحة الطالب فوق الحالة التأليفية؛ `resetLessonLock` يلغي المنح أيضًا؛ `getNextLesson` مقيّد بـ`tenantId`.
- الأدلة الخام في §14: تحقق DB **15/15** بدور `app_user` · RLS e2e **5/5** · سلسلة **7/7** على قاعدة فارغة · api **229/229** · build 4/4.

**متبقٍ (خارج البند):** أنواع الفتح بخلاف ENTER_* نقاط امتداد مستقبلية؛ والدرس المقفول ما يزال يعيد المحتوى/الفيديوهات في العرض (القفل استشاري — §6.2).
